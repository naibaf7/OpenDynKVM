## Prerequisites

**Software and firmware**
- **Rust** from [rustup](https://rustup.rs) (stable). The firmware directories pin their targets in
  `rust-toolchain.toml`, so rustup installs `thumbv8m.main-none-eabihf`, `thumbv7em-none-eabihf` and
  `riscv32imc-unknown-none-elf` on first use. A distribution `rustc` without these targets (Fedora's, for example)
  won't build the firmware: put `~/.cargo/bin` first in `PATH`.
- **espflash** (`cargo install espflash`) for the Bluetooth module's flash image in `cargo xtask dist`.
- **Windows build of odkvmctl from Linux** (optional): `rustup target add x86_64-pc-windows-gnu` and MinGW-w64.
- odkvmctl's USB access is pure Rust on Windows and Linux: no libudev or C compiler is needed.
- **Installers** (`cargo xtask package`, optional): podman or docker (the Linux packages are built in a Debian 12
  container), `rpmbuild` for the `.rpm`, and NSIS (`makensis`) plus MinGW-w64 for the Windows installer.

**Python scripts** (the hardware generators and checks, the case, the logo, the fonts): [uv](https://docs.astral.sh/uv/)
runs every one of them (`uv run <script>`, from anywhere in the repository), in one environment pinned by
`pyproject.toml` and `uv.lock`: numpy, scipy, shapely and fontTools.  The hardware tools also need `pcbnew`, KiCad's
own Python module, so the environment is built on the Python KiCad comes with, and sees its packages.  Once, from the
repository root:

```sh
uv venv --system-site-packages --python /usr/bin/python3     # Linux: the distribution's Python, which KiCad uses
uv sync
```

On Windows give `--python` KiCad's own `python.exe` (`C:\Program Files\KiCad\10.0\bin\python.exe`), on macOS the
one inside KiCad.app (`/Applications/KiCad/KiCad.app/Contents/Frameworks/Python.framework/Versions/Current/bin/python3`).
`uv run python -c "import pcbnew"` checks the result.  The case generator, `hardware/case/gen_case.py`, brings its
own environment (OpenCascade has no build for every Python KiCad uses): `uv run` sets it up from the script itself.

**Hardware generators** (only to change the board)
- **KiCad 10**: `kicad-cli`, and its `pcbnew` Python module (above).
- A C compiler as `cc`: the router compiles its A* kernel on first use.
- **curl and network access** on the first run: `gen_footprints.py` and `jlc_align.py` fetch part data from EasyEDA into
  a local cache, which is not part of the repository.
- **HarfBuzz's `hb-subset`** for the Chinese UI font (`software/odkvmctl/fonts/make_cjk_font.py`).

**Flashing**: nothing beyond a USB-C cable for the normal paths. Optional: a debug probe via the Tag-Connect TC2030
pads (`probe-rs`), `picotool`, `dfu-util`.

## Build and test

```sh
cargo test                                             # shared crates, odkvmctl and xtask
cargo xtask dist                                       # the firmwares → dist/
cargo xtask package                                    # installers for odkvmctl and opendyn-kvm → dist/
cargo run -p odkvmctl --bin odkvmctl -- --sim status   # the CLI against a built-in simulated KVM
cargo run -p odkvmctl --bin opendyn-kvm -- --sim       # the GUI against the simulator
cargo xtask desktop                                    # Linux: menu entry + icons for target/debug (--remove: undo)
cargo build -p odkvmctl --release                      # odkvmctl and opendyn-kvm for this machine
cargo build -p odkvmctl --release --target x86_64-pc-windows-gnu
OPENDYN_SHOTS=/tmp/shots cargo test -p odkvmctl --bin opendyn-kvm -- --ignored screenshots   # every GUI page as an image
OPENDYN_SIM_BT=1 cargo run -p odkvmctl --bin opendyn-kvm -- --sim   # the same with the Bluetooth module (0.16.0)
OPENDYN_SIM_HOP=1 cargo run -p odkvmctl --bin opendyn-kvm -- --sim  # the same with screen hop set up
OPENDYN_LANG=de cargo run -p odkvmctl --bin odkvmctl -- --sim       # in German (en, fr, de, nb, zh; or Settings → Language)
```

`cargo xtask dist` builds the AT32F405 firmware, then the RP2354B firmware with it embedded, and the Bluetooth
module's image; the files it writes and what each is for are in [software.md §10](software.md).

`cargo xtask package` writes the host software's installers:

| File | For |
|---|---|
| `dist/OpenDynKVM-Setup-<version>.exe` | Windows 10 and 11 |
| `dist/opendyn-kvm_<version>_amd64.deb` | Debian 12 and later, Ubuntu 22.04 and later |
| `dist/opendyn-kvm-<version>-1.x86_64.rpm` | Fedora, openSUSE |

The Linux binaries are built in a Debian 12 container, so they need only glibc 2.35 whatever this machine runs
(`--native` builds them here instead). The `.deb`'s Maintainer comes from `DEBFULLNAME` / `DEBEMAIL`, else from git's
user. Each package includes the licenses of every crate compiled in (`THIRD-PARTY-LICENSES.txt`), and the firmware of
the same tree (`cargo xtask package` runs `dist` first), which the app installs by default. The packages are not
signed yet; details in [software.md §9](software.md).

On Wayland a window shows the icon of the menu entry named after its app id (`opendyn-kvm`): a build run from
`target/` has none and gets the desktop's generic icon until `cargo xtask desktop` puts the entry and the icons into
`~/.local/share`, as the packages do system-wide.

**Running from source on Linux:** the packages install a udev rule and a module setting; without the packages,
install them once yourself:

```sh
sudo cp software/odkvmctl/udev/70-opendyn-kvm.rules /etc/udev/rules.d/
echo i2c-dev | sudo tee /etc/modules-load.d/opendyn-kvm.conf && sudo modprobe i2c-dev
sudo udevadm control --reload && sudo udevadm trigger
```

## Versions

Hardware, firmware and host software each carry a `major.minor.patch` version.

| What | Now | Where it is set |
|---|---|---|
| Hardware | **0.17.0** in design, not ordered yet (0.13.0 to 0.16.0 were designed and never ordered). **0.12.0** is the board ordered as revision 12 | `HW_VERSION` in `hardware/tools/gen_pcb.py` (printed on the board: the design's version) and `kvm_proto::HARDWARE_VERSION` (what the firmware reports: the newest board that was ordered, still 0.12.0) |
| Firmware, RP2354B and both AT32F405s alike | **0.1.11** | `kvm_proto::FIRMWARE_VERSION` |
| Host software (`odkvmctl`, `opendyn-kvm`, the installers) | **0.1.11** | `version` in the root `Cargo.toml` |

- **Hardware:** a new major version is a different board: 1.0.0 will be the mass-production board, 2.0.0 a new design.
  Minor versions are revisions of the same board. When a board is ordered:
  1. Tag the commit that was sent to the fab, `hw-vX.Y.Z` (that tag is the record of what was built).
  2. Set `kvm_proto::HARDWARE_VERSION` to that version.
  3. Bump `HW_VERSION` for the next design, which is then changed in place.

  A revision of an ordered board is routed from that board, so it differs only where it has to: see "Revising an
  ordered board" in [hardware/README.md](hardware/README.md).
- **Firmware:** its version follows the host software's, but it doesn't move with every host release. A release that
  changes the firmware gives it that release's version; a host release without firmware changes leaves it alone. A
  test keeps the firmware from running ahead of the host software.
- **One image per board:** a firmware image is built for one hardware major version and says so in its `FwId`.
  `odkvmctl update` and the app refuse an image for another board. If hardware 2.0.0 needs its own build, each board
  gets an image of the same firmware version.
- **Control protocol:** reported in `Info`. It goes up when the wire format changes ([software.md §8](software.md)).

## Working on the hardware

The KiCad files are **generated**: change the scripts in `hardware/tools/`, never the `.kicad_sch` / `.kicad_pcb` by
hand. The whole chain (symbols, footprints, schematic, ERC, placement, routing, checks, fabrication files) is in
[hardware/README.md](hardware/README.md). In short, from `hardware/`:

```sh
uv run tools/gen_symbols.py && uv run tools/gen_footprints.py && uv run tools/gen_schematic.py
uv run tools/gen_pcb.py --force                    # placement (discards the routing)
uv run tools/route.py --live                       # routing; watch it at http://localhost:8765/
kicad-cli pcb drc --schematic-parity kvm.kicad_pcb
uv run tools/check_copper.py && uv run tools/check_spacing.py && uv run tools/check_aux.py
uv run tools/make_fab.py                           # JLC BOM, CPL, gerbers, drill
uv run case/board_facts.py && uv run case/gen_case.py      # the case, if holes, ports, LEDs or parts moved
```

Always route with `--live` and run the checks after every routing run; the router is not bit-deterministic
([AGENTS.md](AGENTS.md)). Ordering: [hardware/jlcpcb.md](hardware/jlcpcb.md).

## Firmware development

- **Debug probe:** `cd firmware/rp2354 && cargo run --release` flashes over SWD with probe-rs and shows the defmt log
  over RTT (`firmware/at32f405` likewise, on its own Tag-Connect pads). A probe flash overwrites the partition table, so
  USB updates are off until `kvm-first.uf2` is copied again.
- **Keep an AT32F405 build:** the RP2354B reprograms the AT32F405s whenever their firmware differs from the embedded
  image. To test an AT32F405 build flashed by probe, build the RP2354B without one:
  `KVM_AT32_ELF=/nonexistent cargo build --release`.
- **Log without a probe:** `DBG_TX` (pin 6 of the RP2354B's Tag-Connect pads, 115200 8N1) carries a plain-text log of
  boot, self-test, AT32F405 programming and updates.
- **Prototype:** a Pico 2 and an AT-START-F405 board, wired as on the KVM ([software.md §11](software.md), milestone M1).

## Bring-up status

The first board, a 0.12.0, runs firmware 0.1.10. Faults of the board itself, with their workarounds, are in
[hardware/errata.md](hardware/errata.md).

**Verified on that board:**
- Hub-0 enumerates with the errata E1 workaround, and the `RP2350` drive appears on PWR/SERVICE with R510 bridged
  (errata E2): the first flash with only a cable.
- AT32F405 programming over SPI (ST's bootloader protocol, AN4286, which Artery's ROM follows). Every chunk is read
  back, so a mismatch fails the update instead of writing a wrong image.
- Firmware updates over USB from a PC (the app and `odkvmctl update`, confirmed with the key), including the reboot
  into the new image on trial.
- Both PCs, switching between them; keyboard and mouse in the emulated modes, passthrough and back, and mode
  changes; Vial (vial.rocks); screen hop between the two PCs, with two screens on a Windows PC.
- DDC/CI reading two monitors on Linux, one over DisplayPort and one over HDMI.

**Still to check:**
- **A front device that drops off during a PC switch or a mode change.** A receiver once stayed in probing (yellow
  LED) until it was replugged; 0.1.10 ends the old session, replugs the port on Hub-0 a few times, and no longer
  cycles VBUS. Not seen again so far.
- **AT32F405 without its crystal** falls back to the internal oscillator and reports it; that fallback hasn't run on a
  chip yet.
- **AT32F405 USB DFU recovery** (`odkvmctl reboot at32-dfu1|at32-dfu2`, then `dfu-util`): the RP2354B keeps polling the
  chip's SPI link meanwhile, which may make its ROM settle on SPI instead of USB DFU. Use SWD if DFU does not appear.
- **Standby, auto-select and remote wakeup** are tested in the engine only. On the boards, still to see:
  - whether the AT32F405's resume signal passes the PC's USB2514B hub to a sleeping PC;
  - what each PC reports while shut down with standby power (auto-select waits 30 s for a PC with 5 V but no host);
  - the current actually saved.
- **DDC/CI** switching inputs, and the Windows path.
- **The Bluetooth module** (boards from 0.16.0) and the **0.17.0** board with the fixes for errata E2 and E3.
